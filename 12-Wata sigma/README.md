## 1. ไฟล์ในโปรเจกต์

| ไฟล์ | ประเภท | คำอธิบาย |
|------|--------|----------|
| `ledger.c` | Source Code | โค้ดทั้งหมดของโปรแกรม |
| `ledger.txt` | Data File | ข้อมูลตัวอย่างสำหรับทดสอบ (โปรแกรมอ่านและเขียนไฟล์นี้อัตโนมัติ) |
| `README.md` | README | ไฟล์นี้ |
| `benchmark.c` | Source Code (เสริม) | โปรแกรมทดสอบประสิทธิภาพที่ n = 100, 1000, 10000 (include `ledger.c` จึงวัดโค้ดจริงชุดเดียวกัน) |

## 2. เครื่องมือ / ภาษา / Library ที่ต้องใช้

- ภาษา C (มาตรฐาน C99 ขึ้นไป)
- คอมไพเลอร์ `gcc` (Linux / macOS หรือ Windows ผ่าน MinGW-w64 / MSYS2) หรือใช้ Dev-C++ / Code::Blocks ก็ได้
- ไม่ต้องติดตั้ง Library เพิ่ม ใช้เฉพาะ standard library (`stdio.h`, `stdlib.h`, `string.h`, `time.h`)
  และบน Windows ใช้ `windows.h` เพื่อตั้งค่า console ให้แสดงภาษาไทย (มากับ MinGW อยู่แล้ว)
- ตัวอักษรไทยในโปรแกรมและไฟล์ข้อมูลเป็น UTF-8

## 3. ขั้นตอนติดตั้งและวิธีเปิดใช้งาน

ไม่ต้องติดตั้งอะไรเพิ่ม เพียงคอมไพล์ `ledger.c` แล้วรัน **ในโฟลเดอร์เดียวกับ `ledger.txt`**

**Linux / macOS**

```bash
gcc -O2 -Wall -o ledger ledger.c
./ledger
```

**Windows (MinGW / MSYS2, ใช้ Command Prompt หรือ PowerShell)**

```bat
gcc -O2 -Wall -o ledger.exe ledger.c
ledger.exe
```

หมายเหตุ
- ถ้าไม่มี `ledger.txt` โปรแกรมจะเริ่มจากว่างและสร้างไฟล์ให้เมื่อบันทึกครั้งแรก
- โปรแกรมตั้งค่า console เป็น UTF-8 ให้เองบน Windows ถ้าภาษาไทยยังแสดงผลเพี้ยน ให้ลองพิมพ์ `chcp 65001`
  ก่อนรัน หรือใช้ Windows Terminal
- ไฟล์ `.exe` ต้องคอมไพล์ใหม่ทุกครั้งที่แก้ `ledger.c` เพื่อให้ตรงกับซอร์สล่าสุด

## 4. วิธีใช้งาน

เมื่อเปิดโปรแกรมจะพบเมนู เลือกโดยพิมพ์ตัวเลขแล้วกด Enter

| เมนู | การทำงาน |
|------|----------|
| 1 | เพิ่มรายรับ (วันที่ หมวดหมู่ จำนวนเงิน โน้ต) |
| 2 | เพิ่มรายจ่าย |
| 3 | แก้ไขรายการตาม id (เว้นว่าง = ไม่เปลี่ยนค่านั้น, พิมพ์ `-` ที่ช่องโน้ต = ล้างโน้ต) |
| 4 | ลบรายการตาม id |
| 5 | ดูทุกรายการ (เรียงตามวันที่) พร้อมยอดรวม |
| 6 | ดูสรุป: รายวัน / รายสัปดาห์ / รายเดือน / แยกตามหมวดหมู่ |
| 0 | ออกจากโปรแกรม |

รูปแบบที่ต้องกรอก
- วันที่: `YYYY-MM-DD` ปี **ค.ศ.** (1970–2100) เช่น `2026-09-28` (เว้นว่าง = วันนี้)
- สัปดาห์: `YYYY-Www` เช่น `2026-W40` (ตามมาตรฐาน ISO สัปดาห์เริ่มวันจันทร์)
- เดือน: `YYYY-MM` เช่น `2026-09`
- จำนวนเงิน: ตัวเลขมากกว่า 0 ทศนิยมไม่เกิน 2 ตำแหน่ง เช่น `120` หรือ `45.50` (ไม่เกิน 1,000,000,000.00)
- หมวดหมู่ยาวได้ไม่เกิน 63 ไบต์ (ภาษาไทยประมาณ 21 ตัวอักษร) โน้ตไม่เกิน 127 ไบต์ (ประมาณ 42 ตัวอักษร)
  ถ้าเกินโปรแกรมจะตัดให้โดยไม่ตัดกลางตัวอักษร

ถ้ากรอกรูปแบบผิด โปรแกรมจะแจ้งและไม่บันทึก ถ้าปิด input (Ctrl+D บน Linux/macOS, Ctrl+Z แล้ว Enter บน Windows)
โปรแกรมจะออกเอง ข้อมูลจะถูกบันทึกลงไฟล์ทันทีหลังเพิ่ม แก้ไข หรือลบ

ข้อมูลตัวอย่างใน `ledger.txt` (เดือน 2026-09) ควรได้ผลดังนี้ ใช้ตรวจว่าโปรแกรมทำงานถูก

| สรุป | รายรับ | รายจ่าย | คงเหลือ |
|------|-------:|--------:|--------:|
| ทั้งหมด / เดือน 2026-09 | 15700.00 | 415.00 | 15285.00 |
| สัปดาห์ 2026-W40 | 200.00 | 45.00 | 155.00 |

## 5. รูปแบบไฟล์ข้อมูล (`ledger.txt`)

หนึ่งบรรทัดต่อหนึ่งรายการ คั่นด้วยเครื่องหมาย `|`

```
id|วันที่|ประเภท|หมวดหมู่|จำนวนเงิน|โน้ต
2|2026-09-01|0|อาหาร|50.00|ข้าวมันไก่
```

ประเภท: `1` = รายรับ, `0` = รายจ่าย

ถ้าแก้ไฟล์ด้วยมือ โปรแกรมจะข้ามบรรทัดที่อ่านไม่ได้ (รูปแบบผิด วันที่ไม่จริง จำนวนเงินไม่ถูกต้อง)
และแจ้งจำนวนบรรทัดที่ข้าม รองรับไฟล์ที่มี BOM และ CRLF

## 6. โครงสร้างข้อมูลที่ใช้

ใช้ **Array** (Dynamic Array) เก็บรายการรายรับ-รายจ่ายในตัวแปร `Transaction *data`
เมื่ออาร์เรย์เต็มโปรแกรมจะขยายขนาดเป็น 2 เท่าด้วย `realloc`
จำนวนเงินเก็บเป็นจำนวนเต็มหน่วยสตางค์ (`long long`) เพื่อไม่ให้ผลรวมคลาดเคลื่อนแบบ `double`

| การทำงาน | ความซับซ้อน |
|----------|-------------|
| เพิ่มรายการท้ายอาร์เรย์ (รวมเขียนต่อท้ายไฟล์) | O(1) โดยเฉลี่ย |
| เข้าถึงตาม index | O(1) |
| ค้นหา / แก้ไข / ลบตาม id | O(n) |
| สรุปรายวัน/สัปดาห์/เดือน | O(n) |
| ดูทุกรายการ (เรียงวันที่) | O(n log n) |
| สรุปตามหมวดหมู่ (เรียงแล้วจัดกลุ่ม) | O(n log n) |

การเพิ่มรายการใช้การ append ท้ายไฟล์ จึงเป็น O(1) จริงทั้งในหน่วยความจำและบนไฟล์
ส่วนการแก้ไขและลบต้องเขียนไฟล์ใหม่ทั้งไฟล์ (O(n)) โดยเขียนลงไฟล์ชั่วคราวก่อนแล้วค่อยแทนที่ `ledger.txt`
ถ้าโปรแกรมหยุดกลางคันข้อมูลเดิมจึงไม่เสียหาย

## 7. ผลทดสอบประสิทธิภาพ (Benchmark)

คอมไพล์และรัน: `gcc -O2 -o benchmark benchmark.c && ./benchmark` (ใช้เวลาประมาณ 10 วินาที)

แต่ละการทำงานรันซ้ำหลายรอบแล้วหาเวลาเฉลี่ยต่อ 1 ครั้ง และรันทั้งชุด 3 รอบเลือกรอบที่เร็วที่สุด
ข้อมูลทดสอบสร้างแบบสุ่มด้วย seed คงที่ ค่าด้านล่างเป็นไมโครวินาทีต่อ 1 การทำงาน

สภาพแวดล้อมที่วัด: Linux บนเครื่องเสมือน Intel Xeon (L1d 48 KB, L2 2 MB), gcc 13.3 -O2, glibc 2.39
รัน 2 รอบได้ผลต่างกันไม่เกิน 2% ผลบนเครื่องอื่นจะต่างกันได้ ควรรันซ้ำบนเครื่องที่ใช้นำเสนอ

| การทำงาน | n=100 | n=1000 | n=10000 | x(100->1k) | x(1k->10k) | Big O |
|----------|------:|-------:|--------:|-----------:|-----------:|-------|
| เพิ่มรายการ (ต่อ 1 รายการ, ในหน่วยความจำ) | 0.007 | 0.009 | 0.010 | 1.2 | 1.2 | O(1) เฉลี่ย |
| ค้นหาตาม id (แย่สุด) | 0.034 | 0.334 | 3.359 | 9.8 | 10.0 | O(n) |
| ลบรายการแรก (แย่สุด) | 0.120 | 3.644 | 49.570 | 30.5 | 13.6 | O(n) |
| สรุปรายเดือน | 0.406 | 4.007 | 48.089 | 9.9 | 12.0 | O(n) |
| สรุปรายสัปดาห์ | 70.571 | 708.890 | 7096.240 | 10.0 | 10.0 | O(n) |
| เรียงตามวันที่ | 3.753 | 93.153 | 1710.685 | 24.8 | 18.4 | O(n log n) |
| สรุปตามหมวดหมู่ | 3.519 | 69.318 | 1386.345 | 19.7 | 20.0 | O(n log n) |

อัตราส่วนที่คาดหวังเมื่อ n เพิ่ม 10 เท่า: O(1) ~1x, O(n) ~10x, O(n log n) ~15x (100->1k) และ ~13x (1k->10k)

ตารางนี้วัดเฉพาะการทำงานในหน่วยความจำ ไม่รวมเวลาเขียนไฟล์

### อ่านผล

- **เพิ่ม** ใกล้เคียง 1x ตรงกับ O(1) โดยเฉลี่ย (การขยายอาร์เรย์เป็น 2 เท่าถูกกระจายไปทุกรายการ)
- **ค้นหา สรุปเดือน สรุปสัปดาห์** โตประมาณ 10x ต่อ n เพิ่ม 10 เท่า ตรงกับ O(n)
  สรุปรายสัปดาห์ช้าที่สุดเพราะเรียก `mktime` เพื่อหาเลขสัปดาห์ของทุกรายการทุกครั้ง
  (ประมาณ 0.7 µs ต่อรายการ เทียบกับสรุปเดือนที่เปรียบเทียบสตริงอย่างเดียว)
- **ลบ** ที่ n=100->1k ขึ้น 30x ทั้งที่คาดไว้ 10x เวลาส่วนใหญ่คือ `memmove` ข้อมูลขนาด `sizeof(Transaction)` = 224 ไบต์
  ต่อรายการ คำนวณจากตัวเลขได้ว่าความเร็วคัดลอกลดจากราว 185 GB/s (22 KB) เป็น 61 GB/s (224 KB) และ 45 GB/s (2.2 MB)
  สอดคล้องกับข้อมูลที่หลุดจาก L1 (48 KB) ไปอยู่ L2 แต่นี่เป็นการอนุมานจากตัวเลข ยังไม่ได้วัดด้วย performance counter
- **เรียงและสรุปหมวดหมู่** โตเร็วกว่า n log n เล็กน้อย (ประมาณ 18-25x แทน 13-15x) ทดลองเพิ่มเติมแยกต่างหาก
  เรียงข้อมูลสุ่มที่ n ตั้งแต่ 1,000 ถึง 32,000 ได้ต้นทุนต่อ n log n เพิ่มขึ้นราว 40% เมื่อ record ใหญ่ 224 ไบต์
  แต่เพิ่มราว 11% เมื่อ record เล็ก 16 ไบต์ แสดงว่าขนาด record มีผล แต่ก็เป็นหลักฐานจากเครื่องเดียว
  ยังไม่พอสรุปแน่ชัดว่าเกิดจาก cache หรือวิธีที่ `qsort` ของ glibc จัดการ record ขนาดใหญ่

### ข้อควรระวังของ benchmark

การลบแก้ข้อมูลในอาร์เรย์ (เติมสำเนาท้ายอาร์เรย์) benchmark จึงลบบนอาร์เรย์ที่สร้างแยกไว้ใช้เฉพาะการลบ
ไม่เช่นนั้นที่ n=100 และ 1000 ข้อมูลทุกรายการจะกลายเป็นสำเนาเดียวกันหมดก่อนถึงขั้นตอนเรียง
ทำให้ตัวเลขการเรียงและสรุปหมวดหมู่ต่ำผิดจริง และอัตราส่วนที่ n=10000 สูงผิดปกติถึง 46-57x
(README ฉบับก่อนหน้าเคยอธิบายค่า 46-57x นี้ว่าเป็นผลของ cache ซึ่งไม่ถูกต้อง)
