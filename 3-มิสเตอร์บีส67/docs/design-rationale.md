# เหตุผลการเลือกโครงสร้างข้อมูลและอัลกอริทึม (Design Rationale)

เอกสารนี้อธิบายว่าทำไมโปรเจกต์ SmartBudget เลือกใช้โครงสร้างข้อมูล/อัลกอริทึมแต่ละแบบ
และทำไมไม่เลือกทางเลือกอื่นที่ดูเหมือนจะง่ายกว่า พร้อมอ้างอิงจากผลวัดประสิทธิภาพจริงใน
`tests/benchmark-results.md`

---

## 1. เก็บรายการธุรกรรม: Doubly Linked List vs Array

| ประเด็น | Array ธรรมดา | Doubly Linked List (ที่เลือกใช้) |
|---|---|---|
| เพิ่มรายการใหม่ (append) | O(1) amortized | O(1) |
| ลบรายการกลาง list | O(n) — ต้องขยับข้อมูลทุกตัวที่อยู่หลัง | O(1) — เมื่อมี pointer ไปยัง node นั้นแล้ว (จาก index map) |
| เดินย้อนกลับ (ล่าสุด -> เก่าสุด) | ต้อง reverse() ทั้ง array ก่อน หรือ loop ย้อน index O(n) พื้นที่เพิ่ม | เดินผ่าน `prev` ได้ทันที ไม่ต้องสร้างสำเนาข้อมูล |

**เหตุผลที่เลือก Linked List:** ธุรกรรมถูกลบบ่อย (ผู้ใช้แก้ไข/ลบรายการที่กรอกผิดได้ตลอดเวลา) การลบกลาง
Array ต้องขยับข้อมูลทุกตัวที่อยู่ด้านหลัง ซึ่งแพงขึ้นเรื่อยๆ เมื่อข้อมูลมากขึ้น ในขณะที่ Linked List ลบได้
ทันทีโดยแค่เปลี่ยนตัวชี้ 4 ตัว (`prev`/`next` ของเพื่อนบ้านสองฝั่ง) นอกจากนี้หน้า Dashboard ต้องการแสดง
"รายการล่าสุด" (เดินจาก tail ย้อนกลับ) ซึ่ง Doubly Linked List ทำได้โดยตรงผ่าน `prev` โดยไม่ต้องคัดลอก/reverse
ข้อมูลเหมือน Array

**ข้อเสียที่ยอมรับ:** การเข้าถึงรายการที่ตำแหน่งที่ n (random access) ทำไม่ได้ใน O(1) เหมือน Array —
แต่โปรแกรมนี้ไม่มีการเข้าถึงแบบสุ่มตามตำแหน่ง (ใช้ id ค้นหาผ่าน index Map แทน ซึ่งเป็น O(1) อยู่แล้ว)
จึงไม่กระทบการใช้งานจริง

## 2. ค้นหาตามช่วงเวลา: AVL Tree vs Array + Sort ใหม่ทุกครั้ง

| ประเด็น | Array + sort() ทุกครั้งที่ค้นหา | AVL Tree (ที่เลือกใช้) |
|---|---|---|
| เตรียมข้อมูลก่อนค้นหาครั้งแรก | ไม่ต้อง | ต้อง insert ทีละตัว O(log n) ต่อครั้ง |
| ค้นหาครั้งที่ 2 เป็นต้นไป (ข้อมูลไม่เปลี่ยน) | ยังต้อง sort ใหม่ทุกครั้ง O(n log n) ถ้าไม่ cache ผลไว้ | O(log n + k) ทุกครั้ง (k = จำนวนผลลัพธ์ในช่วง) |
| หลังเพิ่ม/ลบข้อมูล 1 รายการ | ต้อง sort ใหม่ทั้งก้อน O(n log n) | แค่ insert/remove เพิ่ม O(log n) ต้นไม้ยังเรียงอยู่เสมอ |

**เหตุผลที่เลือก AVL Tree:** ผู้ใช้ค้นหาธุรกรรมย้อนหลังบ่อย (หน้า Search) และข้อมูลเปลี่ยนแปลงตลอดเวลา
(เพิ่ม/ลบ/แก้ไขรายการ) ถ้าใช้ Array + sort ใหม่ทุกครั้งที่ค้นหา จะเสียเวลา O(n log n) ซ้ำๆ ทุกครั้งที่กดค้นหา
แม้ข้อมูลจะไม่เปลี่ยนเลยก็ตาม ส่วน Binary Search Tree ธรรมดา (ไม่ self-balancing) มีความเสี่ยงที่ถ้า insert
ข้อมูลตามลำดับเวลา (ซึ่งเป็นกรณีปกติของธุรกรรมการเงิน — วันเวลาเพิ่มขึ้นเรื่อยๆ) ต้นไม้จะเบี้ยวจนกลายเป็น
linked list (O(n) ต่อการค้นหา) — ผลทดสอบใน `tests/test-suite.js` ("insert แล้วต้นไม้สมดุล") ยืนยันว่า AVL Tree
คงความสูงใกล้เคียง log2(n) แม้ insert ข้อมูลเรียงลำดับ 1,000 รายการติดต่อกัน (กรณีที่ BST ธรรมดาจะพังเป็นเส้นตรง)

## 3. สรุปยอดตามหมวดหมู่: Hash Table (เขียนเอง) vs Object/Map ของ JavaScript

**เหตุผลที่เขียน Hash Table เอง (แทนใช้ `{}` หรือ `Map` ของ JS ตรงๆ):** เพื่อแสดงให้เห็นกลไกการทำงานจริง
ของ Hash Function (DJB2 hashing) และการจัดการ collision ด้วย Separate Chaining ตามเป้าหมายของวิชา
ที่ต้องอธิบายโครงสร้างข้อมูลได้ ไม่ใช่แค่เรียกใช้ library สำเร็จรูป — ในแง่ความซับซ้อนเชิงเวลา
`{}`/`Map` ของ JS ก็เป็น O(1) โดยเฉลี่ยเหมือนกัน (เพราะภายในคือ hash table อยู่แล้ว) ข้อแตกต่างหลักคือ
เวอร์ชันที่เขียนเองสามารถดูการกระจายตัวของข้อมูลใน bucket ได้จริง (หน้า Data Structure & Algorithm)
ซึ่งเป็นสิ่งที่ `{}`/`Map` ไม่เปิดให้ตรวจสอบจากภายนอก

## 4. จัดเรียงข้อมูล: Quick Sort vs Merge Sort (ทำไมมีทั้งคู่)

ไม่ได้เลือกอย่างใดอย่างหนึ่งแทนอีกอย่าง เพราะทั้งสองมีจุดแข็ง-จุดอ่อนต่างกันและใช้คนละจุดประสงค์ในระบบ:

- **Merge Sort** เป็น **stable sort** (รายการที่มีค่าเท่ากันจะไม่สลับลำดับเดิม) จึงใช้เป็นอัลกอริทึมเริ่มต้นของ
  หน้า Search เพื่อให้ผลลัพธ์คาดเดาได้ (เช่น ธุรกรรมวันเดียวกันจะเรียงตามลำดับที่กรอกเข้าระบบเสมอ) และมี
  worst-case O(n log n) การันตีแน่นอน ไม่มีกรณีที่แย่ลงเป็น O(n²)
- **Quick Sort** ใช้ในหน้า Benchmark เพื่อเปรียบเทียบให้เห็นว่าในทางปฏิบัติ Quick Sort มักเร็วกว่า Merge Sort
  จริง (ใช้หน่วยความจำน้อยกว่าเพราะ sort แบบ in-place ไม่ต้องสร้าง array ใหม่ตอน merge) แต่มีความเสี่ยงที่
  worst-case จะแย่ลงเป็น O(n²) ถ้าเลือก pivot ไม่ดี (เช่น ข้อมูลเรียงอยู่แล้วกับ pivot ที่เลือกเป็นตัวสุดท้ายเสมอ)
  ผลวัดจริงใน `tests/benchmark-results.md` ยืนยันว่า Quick Sort เร็วกว่า Merge Sort ในทุกขนาดข้อมูลที่ทดสอบ
  (100 / 1,000 / 10,000 รายการ) สอดคล้องกับทฤษฎี

## 5. Budget Optimization: Greedy vs 0/1 Knapsack (DP) — ทำไมมีทั้งคู่

| ประเด็น | Greedy Algorithm | 0/1 Knapsack (DP) |
|---|---|---|
| Complexity | O(n log n) | O(n × ยอดเงินที่เกินงบ) |
| ผลลัพธ์ | เร็ว แต่**ไม่การันตี**ว่าผลกระทบรวมต่ำที่สุดเสมอ | ช้ากว่า แต่**การันตี**ว่าผลกระทบรวมต่ำที่สุด (optimal) |
| เหมาะกับ | ข้อมูลจำนวนมาก ต้องการคำตอบเร็ว | ข้อมูลไม่มาก ต้องการคำตอบที่ดีที่สุดจริงๆ |

**เหตุผลที่มีทั้งสองแบบให้เลือก:** Greedy เลือกตัดรายการ necessity สูงสุดก่อนเสมอ ซึ่ง "ดูสมเหตุสมผล"
แต่ไม่ได้การันตีว่าจะให้ผลกระทบรวมน้อยที่สุดในทุกกรณี (เช่น ถ้ารายการ necessity 5 มีมูลค่าน้อยมากหลายรายการ
แต่ necessity 4 มูลค่าพอดีเป๊ะกับยอดที่เกิน Greedy อาจตัดเกินความจำเป็นจากรายการ necessity 5 ก่อนโดยไม่จำเป็น)
ในขณะที่ Knapsack คำนวณหาคำตอบที่ดีที่สุดจริงด้วย Dynamic Programming แต่แลกมาด้วยเวลาที่มากกว่า โดยเฉพาะ
เมื่อยอดเงินที่เกินงบมีค่าสูง (ตาราง DP มีขนาดตามยอดเงิน ไม่ใช่แค่จำนวนรายการ)

ผลทดสอบ `tests/test-suite.js` ("Knapsack ให้ผลประหยัดดีกว่าหรือเท่ากับ Greedy เสมอ") และผลวัดความเร็วจริงใน
`tests/benchmark-results.md` ยืนยันทั้งสองประเด็นนี้ตรงกับทฤษฎี: Knapsack ให้ผลกระทบรวมต่ำกว่าหรือเท่ากับ
Greedy เสมอ แต่ช้ากว่า Greedy ถึง 17–96 เท่าขึ้นอยู่กับขนาดข้อมูล — จึงให้ผู้ใช้เลือกสลับโหมดได้เองตามความ
เหมาะสมของสถานการณ์ แทนที่จะบังคับใช้แบบใดแบบหนึ่งตายตัว
